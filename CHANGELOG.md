## [Unreleased]

### Added

- The mobile gate runs on a physical Android device over USB: `node test/mobile/run.mjs --platform=android --android-serial=<serial>` (the serial from `adb devices`, USB debugging authorised, the screen unlocked). It opens one tab in the device's own Chrome and closes it. It installs nothing, stops no browser, and touches neither the debug app nor Chrome's command-line file. It restores the rotation settings that the rotation scenario changes, and the report names the device. On a Pixel 7 Pro (Android 17, Chrome 156, which has no native API, so the polyfill ran as users get it, DPR 2.625) on 2026-10-30, all 11 scenarios PASS with their controls red, `controls` with 62 of 62 regions within 1.5 %. On a Huawei Mate 10 Pro (Android 10, EMUI, Chrome 156, with a display-size override that gives DPR 2 and a 360 x 600 css px viewport) on the same day, the same 11 scenarios PASS with their controls red, twice in a row, `controls` again 62 of 62. iOS is still verified on the simulator only.
- G-regress-capture checks that a listbox select under the canvas, one of them of fractional height, is scrolled to its selected option exactly as the engine scrolls the same select on the plain page (DPR 1 and 2 in the gate; also measured at 1.25 and 1.5). Its control scrolls the polyfill page's listboxes 2 px further. The mutant `listbox-reveal-rounded-scale` (CI) restores the rounded scale and is caught.

Test tooling: the PNG decoder reads 16-bit images (the iPad's wide-colour screenshots), a WebDriver evaluation longer than 30 s raises the session's script timeout first (the driver answered 408 otherwise), and a transient "device is not paired" answer of `safaridriver` is retried.

### Fixed

- The mobile gate on a physical Android phone no longer hangs after the `keyboard` scenario. The scenario scrolled the late field to a fixed 600 css px above it, which on the Mate 10 Pro's 600 css px viewport put the field just below the viewport. The OS tap at its centre then landed on the system's Home key: Chrome went to the background, and in the hidden tab `requestAnimationFrame` and CDP touch input waited for good. Every later scenario timed out, the controls included. The polyfill was not involved; the plain page has the same layout. The field is now placed in the lower half of the viewport, wholly inside it. An OS tap or long press whose point is outside the visual viewport is refused instead of sent. The tab is checked to be visible before and after each OS gesture: if it is not, the scenario fails and the browser is brought back to the front. Under a display-size override the calibration taps are placed from the display size and the css-to-input scale is measured; without one the mapping is unchanged. A first navigation that lands on Chrome's network error page is retried twice.
- The mobile gate's explainer types "Hello" instead of "hello". SwiftKey capitalised the first letter of the empty field from the key events `adb input text` sends, also with `autocapitalize="off"` or `"none"`, `autocorrect="off"` and `spellcheck="false"` (Chrome asks for no capitalisation either way). Sentence-case text comes out as sent, and the comparison is still exact.
- `npm run test:examples`, playground: the click on the drawn field lost its press now and then (the macOS runner, twice). A move and a press sent back to back into the out-of-process preview frame went to the page when the frame did not get pointer events yet: in headless Chrome 156 23 of 65 presses into a just-created preview were lost. The check now hovers until the frame itself reports the pointer, then presses once, as a hand moves before it presses: 0 of 50 lost, also with the CPU throttled 4x. The focus check and the misclick control are unchanged.
- A listbox select (`<select size>` or `multiple`) under the canvas is scrolled to its selected option exactly as the browser scrolls it. Its scale was read as `offsetHeight / getBoundingClientRect().height`, and `offsetHeight` is rounded to a whole css px. On a box of fractional height, which is common at a fractional device pixel ratio, that ratio is not 1 although nothing is transformed. On Chrome for Android at DPR 2.625 a size-3 listbox (52.524 css px, `offsetHeight` 53) was scrolled 34.67 px instead of the browser's 33.90, and its options were drawn 2 device pixels too high. The scale now comes from the fractional layout size (`util/box-scale.js`). The scrollport height is the fractional one too, which matches Chrome at DPR 1, 1.25, 1.5, 2 and 2.625 on 18 listboxes each. The same rounded ratio is gone from the seven other places that used it: the snapshot's listbox scroll and overlay thumb, the clipping ancestors' visible rect, the caret of inputs without a selection API, the text-input overlay, the Safari slider press test and the effect host's canvas box.
- The mobile gate's `controls` scenario no longer has its own 4 % bound for the scrolled light listbox on Android. That deviation was the bug above, not the browser drawing the text differently inside the snapshot. Every one of the 62 regions is now held to 1.5 %.
- A rejected tile decode now says whether the SVG the polyfill generated was well-formed XML. A field test on an iPad Pro (iPadOS 27.2, Safari 27.2) logged one `internal error in snapshot-store:decode: EncodingError: Loading error.` in about 1,400 builds; the store kept the previous pixels, re-damaged the rect (`redamaged: 1`) and the retry landed. Measured on the same iPad, WebKit gives exactly that message for an SVG that is not well-formed XML (an unclosed or mismatched tag, an undefined entity, a root that is not `<svg>`), while a source change during the decode reads `Aborted by source change.` and a 20 MB SVG or 300 concurrent decodes load. The failure therefore points at the generated markup, not at memory or a race, and stays a `console.error`. The message now carries the parser's first error and the markup around it, so the next report names the construct; 1,212 decodes of a scripted run of the field test on the iPad were all well-formed, and the failure did not recur.
- The field test labels iPadOS Safari `ios` in its summary and file name. iPadOS sends the user agent of a Mac, so an iPad Pro report said `device: "macos"`; a Mac user agent with more than one touch point is now an iPad, as the polyfill itself classifies it (Chrome and Firefox for macOS stay `macos`).
- The field test's typing latency no longer counts keys that change no pixel. The caret is hidden while the step measures, so a space typed at the end of the text has no canvas update of its own: it stayed pending and was timed by the next letter, which made the tester's pause part of its latency. The iPad Pro report of 2026-10-30 (16 keys, median 58 ms) had exactly two slow keys, 534 and 651 ms, and `hello field test` has two spaces. Such keys are now listed in the new `steps.typing.results.perKey` (key kind, time, latency) and counted in `invisible`, but not timed. The last key was also timed late: the step paused for 400 ms without reading frames as soon as the text was complete, so a last key still waiting for its update read 400 ms or more (409 ms on the iPad with scripted keys). The step now ends only after that update. Measured on the iPad with scripted keys 450 ms apart: 14 timed keys, 22 to 28 ms. `scripts/check-field-test.mjs` checks both cases and the labels.

## [0.1.0-preview.14] - 2026-10-30

A playground, and a fix for every page that sets a form control from a script. `examples/playground/` on the project's site edits and runs the explainer example in a sandboxed preview, with links that share the code. A script write to a control's state (a slider's or field's value, a checkbox, a select) was repainted only when other damage happened to cover the control, so a slider set from code could show its old thumb beside the new one; it is now repainted. On Safari a list with a classic scrollbar, author-styled or the system's, is composed while it scrolls instead of being rebuilt at every step, and the bar's thumb is drawn where Safari puts it. The documentation was audited end to end.

### Added

- `examples/playground/`, published with the site: edit the explainer example in a plain editor and run it in a preview frame with the core and engines bundles. The preview is `<iframe sandbox="allow-scripts">` without `allow-same-origin` (its document a `data:` URL: Safari hides the messages of errors in a sandboxed `srcdoc` document), so code from a shared link runs in an opaque origin, never in the site's; the polyfill installs, paints and takes typing there in Chrome, Firefox and Safari. A "Show canvas bounds" checkbox, on by default, outlines the canvas in the preview (a base style before the code). A status line says what ran (the polyfill and its mode, the native API, a refusal or a bundle that did not load) and a console panel shows the preview's errors, rejections and console output as text. Share puts the code in the link's fragment (base64url of UTF-8, at most 16,000 characters); a preview that stops answering is reported, and in Chrome Run and Reset recover from it. Linked from the README and GETTING-STARTED.
- `npm run test:examples` runs the playground: install and mode from the status line, the preview canvas not blank, the default code equal to examples/basic's explainer block, the sandbox and the opaque origin, trusted typing in the preview, messages heard only from the preview, user errors shown as text, Share and reload with non-ASCII code, damaged and too-long links, Reset, one frame after five runs, and recovery from an endless loop. Control C5 serves five broken variants of the page (`allow-same-origin`, console text set as HTML, messages from any window, the previous frame kept, canvas bounds never switched off) and each must turn its check red. `npm run test:pages` checks the playground's install and preview on the assembled site.

- Scroll compositor on Safari (macOS): a scroller with an author-styled classic bar (`::-webkit-scrollbar` with a width) is composed, as one with overlay bars is. It was refused (every non-Chromium classic bar was), so each scroll step built a whole snapshot tile. The thumb is moved by WebKit's own geometry, which Safari computes in whole css px: length `round(visible / total x track)` and at least the thumb's laid-out height (`height: auto` is 17 px; `min-height`, `max-height` and a px `height` apply), no thumb when that minimum does not fit, and an offset truncated to a whole css px, an offset under 1 px shown as 1. Measured on Safari 27.0.1 at DPR 2 against the plain DOM (10-14 px bars over 372, 2480 and 31000 px of content, 9-19 offsets each): every thumb edge on the predicted css px. Under a rounded scroller the bar's track is drawn source-over the backdrop, as the pages are. Composed-scrolling fixture with an 11 px styled bar, scripted scroll: 0 of 294 steps composed and 296 snapshot tiles built before, 291 of 294 composed and 5 tiles (the pages) after; on this MacBook Pro the plain path also painted every step (about 46 updates per second at the automation window's frame cadence in both), so the gain there is the main-thread work of a build per step (clone 1 / 2 ms and decode 3 / 3 ms at p50 / p95). Every composed frame equals the settled canvas (G-xbrowser scrollCompose). Still refused: bar buttons and track margins, a thumb length in % or fractional px, iOS / iPadOS, and every Gecko bar.

### Fixed

- A form control whose state a script writes is repainted. The value of a slider or field, the checkedness of a checkbox or radio and the selected option of a select reflect no attribute, so `range.value = '30'` and the like (`valueAsNumber`, `valueAsDate`, `checked`, `indeterminate`, `selectedIndex`, `option.selected`, `textarea.value`, `stepUp()`, `stepDown()`, `setRangeText()`, `form.reset()`) changed the control's pixels without any damage: the control was repainted only where other damage happened to cover it. In the plugin gallery the CRT effect's Glow slider showed two thumbs after choosing the Monitor preset and then Arcade with the mouse: the preset writes every slider's value and the percentage beside it, the percentage's damage covered only the right end of each slider, and the snapshot of the select, built in a microtask of its `change` event, ran before the plugin's own `change` listener had written the values (a microtask runs between the listeners of a real event, not of a scripted one, which is why a scripted preset change looked right). Reproduced in Chrome with real clicks on the drawn select and keys in its popup: after Monitor then Arcade the form's surface differed from a full rebuild in 448 px, the two Glow thumbs; 11 px after the fix (the antialiased edges of partial tiles). The effect's texture was not at fault: a copy of every partial upload kept beside the surface equalled it after every step. The setters and methods are now wrapped (`schedule/observers/control-state.js`, restored at uninstall): a write that changed the state damages the control (an option its select, a checked radio its group, a reset its form) one microtask later; a write of the state the control already has damages nothing. Unit tests (each kind of write against a full rebuild, with the positive control that each write changes the picture; a write of the current state paints nothing), G-regress-paint M7 (two preset changes on a CRT-like slider grid, each against a fresh page) and the mutant `control-state-ignored` (60 mutants).
- Safari: the author-styled vertical bar's thumb is drawn with WebKit's geometry (above). It used the generic (Chromium) one, with a 20 px minimum and a fractional offset; against the plain DOM the thumb now has Safari's length, and in a list on a fractional css position its ends may sit one device row off (the snapshot image snaps box edges to whole css px).

Against the plain DOM at rest (composed-scrolling fixture, 4 offsets): the rounded list's gutter 1.2 % over 100 before, 0 after; the square list's 2.4 % before, 1.2 % after, which is the whole bar one device row off at that list's fractional css position (knob and lane alike, the knob on the twin's rows within the lane). The vertical knob is now a box of its own in the clone, which the compositor captures apart from the lane.

## [0.1.0-preview.13] - 2026-10-30

Conformance with the newest official tests, and privacy fixes for SVG resources. The WPT HTML-in-Canvas tests are pinned at their newest revision (2026-10-28, 248 files): the polyfill passes 214 files and 333 of 381 subtests, against native Chrome's 236 and 369, with no polyfill bug open. An SVG filter outside every drawable canvas is ignored instead of applied, a cross-origin `feImage` in the drawable's own backdrop filter no longer taints the canvas, a copied resource never shows a `:visited` style, and a drawable in the top layer has no snapshot, as natively. On Safari the caret of `caret-color: auto` is drawn in the system accent. Firefox 158 and later draw disabled form controls in new colours, which the polyfill now follows. New checks: text weight against native at DPR 1, and the explainer's position, focus ring and caret on Firefox and Safari.

### Fixed

- Privacy and conformance of SVG resources outside the drawable, re-measured on Chrome Canary 159 (Chromium "Disallow canvas-external SVG filters"): what decides is where the resource lies. A filter, mask, clip path, gradient, pattern or marker inside any canvas with `content=drawable` applies, also outside the drawable (masks and patterns there were masked away or ignored, paint servers and markers dropped); outside every such canvas a clip path applies, a mask masks its element away, and a filter, paint server or marker is ignored (an outside filter used to be applied). A copied resource keeps the computed values of its painting properties, so a selector that depends on its place in the page still applies and a `:visited` style never does. Filters of an external `<use>` document are ignored too. WPT `privacy/filtered-outside-subtree-ignored`, `privacy/svg/svg-mask-filter`, `privacy/svg/svg-mask-nested-filter`, `privacy/svg/svg-pattern-filter-transformed-text`.
- Inside a mask, pattern or marker copied from outside the drawable, an element whose filter is ignored because its `feImage` is cross-origin also loses the filters of its descendants, as natively (it drew a same-origin flood there that native strips).
- The drawable's own `backdrop-filter`, applied by the draw through `ctx.filter`, keeps only `url()` filters inside a drawable canvas whose images are same-origin. A filter with a cross-origin `feImage` TAINTED the canvas (`getImageData` threw a SecurityError); one outside the canvas was applied. The rest of the filter list still applies, as natively.
- A drawable inside a modal dialog, an open popover or a fullscreen element of its canvas has no snapshot: `drawElementImage` and `captureElementImage` throw `InvalidStateError` while it is in the top layer and after it leaves until the next paint (WPT `error-conditions`, Chromium "Suppress snapshot generation for drawables in top layer"). Showing or closing a dialog, toggling a popover and a fullscreen change now repaint the drawables inside.
- A change to an SVG resource outside every drawable (an attribute, its content, the resource or a subtree holding it added or removed) repaints the drawables of its canvas: they draw it by reference.
- Safari (macOS): the caret of a field with `caret-color: auto` is drawn in the system accent, as Safari paints it, instead of the text colour (black on a default field). Measured on Safari 27.0.1 at a blink-on phase: `auto` paints `-apple-system-control-accent` (rgb(0, 122, 255) with the default accent; `accent-color` does not change it, the dark appearance neither) unless the element's colour comes from an author declaration, on the element (inline, a rule, `color: inherit`) or inherited from an ancestor; a colour the UA sheet sets (input, textarea, select, button, mark, a link) does not count and stops that inheritance. An explicit caret-color, `currentcolor` included, is drawn as computed. Safari reads `auto` as the text colour and exposes no origin of a colour, so the engines bundle reads the page's `color` and `caret-color` declarations that apply to the caret's element and its ancestors (inline styles and matching style rules; unreadable cross-origin sheets, nested style rules and presentational attributes are not seen; docs/SUPPORT-MATRIX.md, row `engine-webkit`). Firefox paints `auto` in the text colour (measured by a screen capture), as before; iOS is unchanged.
- Firefox 158 and later: disabled form controls are drawn in the new disabled colours. Firefox 158 (bug 2063178) changed the disabled border, which is also the fill of a disabled checked checkbox or radio, from #8f8f9d at half alpha (light) and opaque #8f8f9d (dark) to #c7c6cb (light) and #515054 (dark) at half alpha, in the same change as `ButtonBorder` (#8f8f9d to #817f84 light, #949297 dark). Pages cannot read the disabled border, so the palette follows the live `ButtonBorder`: #8f8f9d keeps the Firefox 155-157 colours, any other value takes the new ones. Measured on macOS in Firefox 155.0.1, 157.0.1, 158.0 and 159.0. In G-xbrowser `controls` on Firefox 159.0 at DPR 1, the disabled regions went from 3.0-15.2 % of their pixels over 16 (dark checkbox 15.22 %, over the 15 % bound) to 0 %, and the Firefox 157.0.1 numbers are unchanged.

### Changed

- The official WPT HTML-in-Canvas tests are pinned at the newest commit that touches them, `5ccef26d` (2026-10-28; was `850b36a5`, 2026-10-18): 248 files and 381 subtests (was 237 and 369), 11 new files and 13 changed, among them the two Chromium changes that were not exported at the previous pin. The oracle is Chrome Canary 159.0.8128.2, whose imported copy of the tests is byte-identical to the pin (no oracle drift); `test/wpt/oracle-baseline.json` is regenerated from its two full runs. The polyfill passes 214 files and 333 subtests (was 206 and 324), native 236 and 369, the control 11 and 20 (all vacuous); no polyfill bug is open. New reasons: `nested-canvas-filter` (impossible, `drawable-canvas-element`: a canvas painted into and drawn from inside a filtered drawable in the same task), `css-object-fit-nested-canvas` (deviation, `drawable-canvas-element`), `privacy/filtered-outside-subtree-ignored` (impossible, `backdrop-isolation`: its filter checks pass, its descendant backdrop-filter checks cannot). `nested-canvas-scale` moves from impossible to deviation: a canvas that is itself the drawable could be drawn from its live bitmap. The reasons of `nested-geometry` and `caret-selection` are restated with what native does and what blocks the polyfill.
- G-xbrowser `explainer` checks where the content is drawn, as G-explainer does in Chrome: at rest, after typing and with the field focused before typing, the bounding box of the canvas content must sit on the plain-DOM twin's to 1 device px. The twin's form is now clipped to its border box (`clip-path: inset(0)`), as `drawElementImage(form, x, y)` clips it: the default source rect is the border box, and ink a descendant paints beyond it is not drawn (WPT `element-shadow`; measured on Chrome's native implementation: a 4 px outline of the input, which ends at the form's right and bottom edges, is cut at the form's box). The focus rings of Safari (3 css px outside the field) and Firefox (1 px) overflow the form there; the unclipped twin had put the focused box 6 device px (Safari) and 2 device px (Firefox) away from the canvas, which draws them as natively. Now 0 and 1 (Firefox's form is 232.1 css px wide: the last column is partly covered). In Chrome the focus ring of a field is drawn inside its box, so G-explainer is unchanged. New checks with the field focused: the caret colour against the twin's (Safari: the accent, see Fixed; Firefox's WebDriver screenshot draws no caret, so its text colour), and the form drawn with a source rect 8 css px beyond its box, whose content box (the focus ring included) must sit on the unclipped twin's. New mutants `ink-overdraw-default` (a default draw that also shows the ink margin: caught on Safari and Firefox), `ink-margin-zero` (a surface without ink overflow loses the ring a source rect reaching past the form asks for: caught on both) and `webkit-caret-auto-black` (caught on Safari); `shift40-while-focused` is caught on both too. The mutant runner runs a G-xbrowser scenario as a gate (`xbrowser-<scenario>`, headed Safari and Firefox, local only), and `test/xbrowser/run.mjs` prints a gate result line.
- The core bundle grows to 337,120 bytes minified, 113,835 gzipped (+3,373 / +1,184 bytes; 96,600 with brotli), for the SVG resource and top-layer fixes and the caret colour lookup; the engines bundle to 44,143 bytes minified, 16,915 gzipped (+2,567 / +990 bytes), for Safari's caret and Firefox 158's disabled colours (+139 / +52 of them).
- G-pixel-dpr also runs at DPR 1 and compares a text fixture with native (`test/fixtures/text-weight`: light-on-dark and dark-on-light rows at 12, 14 and 16 px in system-ui and Georgia): the canvas must equal native's within the pixel bounds, and every row's ink (the summed coverage of its glyphs) must be within 2 % of native's. Light text on a dark background was suspected to be drawn thinner at DPR 1 on macOS; this does not reproduce in Chrome: the plain page, the polyfill's canvas and native's canvas have the same ink in every row (ratio 1.000) at DPR 1, 1.25, 1.5 and 2, headless and headed, because the SVG image keeps macOS font smoothing, also over transparent pixels (docs/SUPPORT-MATRIX.md, row "text weight"). New mutant `text-smoothing-off`: text set without font smoothing loses 26-30 % of its ink on the light rows and is caught by the new check. Nothing in the polyfill changes.
- G-resize-drag drags at 8 ms in 60 steps (was 30). The page sees one size per rendering update: 30 steps (240 ms) gave 7 to 13 sizes on a loaded machine or runner, under the check's 8, the same for the plain page as for the polyfill's; now 18 to 30.
- The unit tests of a cross-origin `<img>` and `<picture>` wait until the capture has no pending resource (at most 3.5 s) instead of a fixed 300 ms: Windows retries a refused connection before it fails it.
- 56 mutants in all (was 51): `text-smoothing-off`, `ink-overdraw-default`, `ink-margin-zero`, `webkit-caret-auto-black` and `gecko-disabled-palette-swapped`.
- The Firefox launcher of the test harness takes `HIC_FIREFOX_APP`, the path of another Firefox application than `/Applications/Firefox.app` (a release that is not installed, such as the CI runner's). The mutant suite can edit the engines bundle (`bundle: 'engines'`, served to G-xbrowser through `--engines-file`); its first such mutant, `gecko-disabled-palette-swapped`, gives each Firefox release the other release's disabled colours and is caught by G-xbrowser `controls` on Firefox (local only).
- G-platform: a browser session of the probe that does not end within 120 s (one takes 3 to 10 s) fails with the stage it was in, its browser is closed and the probe goes on. Twice on the macOS runner the job had stalled after a DPR 1.25 session until the step's 25 min timeout, with no output saying where.

## [0.1.0-preview.12] - 2026-10-29

Smoother touch scrolling on phones and tablets. On iPhone Safari a touch scroll over a list drawn into a canvas stuttered for a few frames at the start of each gesture: on a page with a `:hover` rule every gesture began with 4 to 9 plain builds (the first composed frame 115 to 268 ms after the first scroll event, iOS Simulator), and on any page the first gesture over a list began with 2 to 3. Now no gesture begins with a plain build, and the first frame lands 1 to 6 ms after the first scroll event. A tap still hovers the tapped element, as natively. Nothing changes with a mouse. The test suite's weaker controls are hardened (G-resize-drag, G-regress-paint, G-explainer, G-scroll-cadence).

### Fixed

- Touch scrolling: a finger puts an element under `:hover` only by a tap, as natively. ### Removed

- **Breaking:** the two-argument `canvas.getElementTransform(element, drawTransform)` and `OffscreenCanvas.getElementTransform(element, drawTransform)` (on the page and in the worker bundle). They belonged to the 2026-10-07 draft; the specification and the official tests removed them on 2026-10-09 (WPT `b59184b6`) and native Chrome no longer has them. The polyfill kept them as deprecated overloads while its conformance gate ran the earlier WPT revision. `canvas.getElementTransform(element)` is unchanged and now ignores a second argument, as WebIDL does, so a call that still passes one returns the stored canvas transform instead of the matrix a draw would store, and the first such call logs one console warning. Instead: draw the element with `drawElementImage` (or call `updateElementGeometry`) and read `canvas.getElementTransform(element)`, or compute the matrix in the page as `S^-1 * D * S` with `D` the draw transform and `S` the scale from css px to the canvas grid (`docs/API-CONTRACT.md` 4.7). On an `OffscreenCanvas`, keep the matrix of your own `drawElementImage` calls; its element geometry reaches the page's canvas, where `getElementTransform(element)` reads it.

### Fixed

WPT `privacy/box-mask-png-ignored`, `box-mask-svg-ignored`, `fragment-mask-png-ignored`, `fragment-mask-svg-ignored`, `svg/svg-mask-on-svg-content-ignored`.
- An SVG `<use>` that refers to another document (`<use href="icons.svg#a">`, or the whole document without a fragment) is drawn when that document is same-origin, with the references inside it resolved against that document; it drew nothing, since the snapshot cannot load external resources. WPT `privacy/svg/svg-use-ignored`.
- A `<video>` with a poster that has loaded but never played shows its poster, as HTML requires while its show-poster flag is set; it showed the first frame. A video whose media data is cross-origin is an invisible box (it keeps its place and paints nothing, its poster included), as read-back-allowed rendering requires; it was a hatched placeholder. Still reported. WPT `privacy/video-ignored` (with the test's `media/white.webm`, which the pinned copy lacks).
- A popover inside a drawable that is shown or hidden (`showPopover()`, `hidePopover()`, `popovertarget`) repaints its drawable: these change no attribute, so the canvas kept the snapshot taken before the toggle (while open the popover is in the top layer and left out, as natively; once hidden, an author `display` draws it in place again). A popover inside an open shadow root is covered too, and so is an image that finishes loading there: neither event leaves its shadow tree. WPT `privacy/popover-show-hide-background-image-ignored`.
- A node moved into a canvas with `moveBefore()` keeps its state as natively: `canvas.moveBefore()` is routed to the canvas's live layer, and a node that reached the canvas through the native method moves on into the layer with `moveBefore()` instead of a remove-and-insert, so an `<iframe>` keeps its document (it reloaded, and the canvas showed its blank initial document in 2 of 6 loads) and focus, animations and playing media are kept. ## [0.1.0-preview.2] - 2026-10-19

A performance release. Scrolling inside a drawable is presented at the display rate in Chrome, effects do no work while their canvas cannot be seen, and snapshot builds read less of the live page. The API is unchanged; `host.stats()` of the effect host gains three fields.

### Performance

- Scrolling inside a drawable is presented at the display rate in Chrome. A live scroller under the pointer (or one that scrolls) is given an invisible main-thread repaint reason, so Chrome's compositor waits for the frame that redraws the canvas instead of delivering the scroll offset in every second frame. Measured at 120 Hz with a trusted wheel stream: a 300-row list from 61 to 113 canvas updates per second (native: 116), with a `:hover` style on its rows from 61 to 61-109 (those steps are built, each hovered row being a change, as often as the main-thread budget allows), rounded corners from 60 to 104, 2000 rows from 4 to 95, the F2 fixture from 24 to 81; main-thread time of the plain list from 36 % to 24 % of the stream. The scroller's look is untouched: its attribute and rule never reach a snapshot, an author transition on `box-shadow` sees no transition from it, and a scroller whose shadow or background is animated, a shadow host and a slotted scroller are left alone (`docs/API-CONTRACT.md` 4.9). Firefox and Safari are not changed by it.
- The scroll compositor plans a scroller when the pointer reaches it (or at its first scroll event), so the first gesture is composed; it keeps its cached pages when something elsewhere in the drawable changes (a counter beside the list), marks the part of the pages a change inside the list touches as stale until the next tile repairs it, composes rounded scrollports (also with a classic scrollbar) inside their rounded clip, and plans scrollers of up to 20,000 elements in steps. Its page builds measure the truncation of a long list once per scroller instead of once per page (2000 rows: page builds p50 6.5 to 5.2 ms).
- `options.maxSnapshotFps` and the `nodeBudget.hard` interval no longer hold the build of a scroller's own scroll damage (rows hovered by a still pointer may ride along); the framecap and the main-thread budget still do. Every other change keeps both limits (`docs/API-CONTRACT.md` 7.1). A 2000-row list now follows every wheel step in Firefox and Safari too (before: 3 to 5 updates per stream of about 60 steps).
- `:hover` rules that only change paint (colours, backgrounds, shadows, outlines, opacity) damage the hovered element alone, also the first time it is hovered.
- The effect host does no work for a canvas nobody can see: while the canvas is more than half a viewport (or half its scroll container) out of view, or the document is hidden, it renders and uploads nothing, `continuous` plugins included (gallery with water: renderer + GPU process CPU from 29 % to 1 %). It renders again before the canvas scrolls back in, and a jump straight into view is rendered in the frame that shows it. The frame clock keeps running, so an effect resumes at the state it has at that time. A `trigger()` or `settled()` that is pending while the canvas is out of view still resolves: the host renders about 10 frames per second until it settles. `host.stats()` gains `paused`, `pauses` and `offscreenFrames`. No option: the pause cannot be seen.
- Snapshot builds read less of the live page, with unchanged output: the clone walk measures the drawable once per build instead of once per list row, reads scroll metrics only of scroll containers and form controls, and no longer creates an `Attr` node per attribute or copies child lists. A parity test builds the examples, the test fixtures and edge cases (transforms, sticky, scrollers, rounded boxes, long lists, shadow DOM, forms, selections) with the walk of 0.1.0-preview.1 and the new one and requires identical snapshots. Per build (p50 / p95 ms, headed Chrome 155, DPR 2): an inner-scroll list of 300 rows 2.11 / 2.54 -> 1.52 / 2.06, the F2 list 4.58 / 6.47 -> 2.89 / 3.68, a 60 Hz counter 1.34 / 1.48 -> 1.05 / 1.22, F4 with 200 elements 1.78 / 3.17 -> 1.31 / 2.25, F4 with 2000 elements 8.53 / 10.28 -> 5.38 / 6.36, typing in a textarea 1.53 / 2.52 -> 1.45 / 2.27.

### Fixed

- Safari Technology Preview as an optional engine of `npm run test:xbrowser` (`stp`): skipped with the reason when it is not installed or its remote automation is off; its native surface is read first. With its HTML-in-Canvas internal feature off it runs the polyfill scenarios and reports the native-flag scenarios skipped; with it on it runs them: install steps aside, the explainer and the contact form drawn natively through the bridge (pixels against the plain-DOM twin, trusted clicks, typing and repaint), uninstall identity and the examples, each with a positive control.
- Text selections are drawn in the colours the engine paints them, in single-line fields and in page text (labels, paragraphs, contenteditable): the system Highlight under the glyphs, the glyphs in HighlightText where Chromium paints a selection foreground (Linux, Windows, ChromeOS, Android) and in their own colour on macOS, an author `::selection` background and colour on every platform, the highlight over the whole line box and the line-break marks of a multi-line selection. Compared with screenshots of the live page on macOS and Linux by `test/unit/snapshot-capture/selection-oracle.driver.mjs`. Windows is not measured; on Firefox and Safari the selection colour is drawn over the glyphs.
- Tests: unit tests in Node and headless Chrome, browser gates with positive controls and a mutation suite, the official WPT HTML-in-Canvas tests at a pinned commit (`docs/CONFORMANCE.md`), Firefox and Safari through WebDriver, and framework apps.

### Known limitations

- The picture lags the DOM by one to two frames, except for the typing and scrolling shortcuts above.
- The children of a drawable canvas are relocated into a live layer next to it; some CSS selectors and live collections can see that layer.
- The core bundle is about 96 KB gzipped, over its original size target.
- Iframes, cross-origin resources without CORS, native UI (select popups, date pickers, IME composition), workers, web views inside apps and Firefox for Android are not supported. Phones and tablets were verified on the iOS Simulator and the Android Emulator only.

See the README and `docs/SUPPORT-MATRIX.md` for the full list.
