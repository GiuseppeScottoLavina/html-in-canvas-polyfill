# Performance comparison: this polyfill, the npm package `html-in-canvas-polyfill` 1.0.1, and native

Three renderers on the same pages, in the same harness, with the same input: **ours** (this repository, `@giuseppe-scotto-lavina/html-in-canvas-polyfill`; `dist/hic-live-polyfill.iife.min.js`, Chrome stable,
no native feature), the **other package** (the unscoped npm package `html-in-canvas-polyfill@1.0.1`, a separate project = `three-html-render` 0.1.2, built by
`test/bench/compare/competitor/build.mjs` with an attribute adapter: it only knows `layoutsubtree`) and **native** (Chrome Canary + `--enable-blink-features=CanvasDrawElement`, no bundle).
Pages: the explainer example, F1 water form (effect off), F2 scroll, F3 resize, F4 large app (200-2000 nodes). Which subject was measured when, all on one machine:
- **ours**: remeasured on 2026-10-31 (14:01-14:33 CET), every row, twice, with the code of 0.1.0-preview.16 plus the two large-drawable fixes released in
  0.1.0-preview.17 (that release's error-message changes came later), on Chrome 156.0.8078.76. The table shows the second run.
- **other package** and **native**: measured on 2026-10-30/31, every row, twice (the other package on Chrome 156.0.8078.76, native on Canary 159.0.8131.0); their code has not changed
  since, so they were not run again. The table shows their second run of that session.

What got worse in this run, plainly: the main-thread cost of an author update in a large drawable at 1,000 and 2,000 elements, mostly in tasks longer than the
8.33 ms frame budget, and startup (parse, compile and install about 2.5 ms slower, the first `paint` event 2.5-3.7 ms later), which follows the 29 % larger core.

What the two fixes recovered, and what remains (the first part of this section has both runs of each):
- **Recovered:** at 1,000 and 2,000 elements, 15.3 and 17.5 ms of main thread per update (24.9 and 34.2 ms with 0.1.0-preview.15, 19.2 and 22.1 ms on 2026-10-15),
  and 1 and 0 of 30 updates with a task over 8.33 ms (25 and 57 before, 0 and 0 on 2026-10-15); the longest task 8.4 and 6.8 ms (11.7 and 22.5 ms before). At 500
  elements, 0 tasks over 8.33 ms (3 before). Update to pixel is unchanged (p50 2-3.5 ms at every size).
- **Remains:** at 200 elements, 16 and 18 of 30 updates in the two passes still run a task over 8.33 ms (23 and 21 before; 6 on 2026-10-15), the longest 9.5 ms,
  at an unchanged 17.7 ms per update: the landing of the whole 200-element tile costs about 8.4 ms by itself, which no split of the build can shorten. Startup is
  unchanged by the fixes (parse, compile and install 10.6 ms, the first `paint` event 19.1 ms after script start; 8.1 and 16.0 ms on 2026-10-15), and so is the
  main-thread cost per update at 200 and 500 elements (17.7 and 14.5 ms, 4.7 and 2.7 times native).

The analysis of 0.1.0-preview.15 that led to the fixes follows. A trace
breakdown of 15 updates at 1,000 elements (`breakdown.mjs --only=f4`, 2026-10-31, against the one of 2026-10-15) finds about the same main-thread total over
all tasks (209 vs 227 ms), but 127 ms of it in 13 tasks over 8.33 ms instead of 36.5 ms in 3: the snapshot's SVG document is parsed
(`DecodedDataDocumentParser::AppendBytes`, 12.7 ms) and laid out (`LocalFrameView::performLayout`, 18.1 ms against 2.6 ms) inside the same long tasks as the
polyfill's script (34.6 ms). The picture lands sooner (update to pixel p50 2-3 ms at every size, against 2-10 ms), but the work that used to be spread over
several tasks now blocks the frame it runs in. The bench's per-update figure (idle subtracted) and the breakdown's total disagree on the size of the increase;
both show the move into long tasks.

**Bisected (2026-10-31)**, with the bench's large-DOM scenario run on core bundles built at each release and commit (headless for the bisection, three interleaved runs per
point), and a probe that records every build (its synchronous ms, whether its decode was split into the next task, the markup length and the number of spacers):

- **The main cause, from 0.1.0-preview.9** (`clone.js`: spacers reach the clone at the live height to the LayoutUnit). To keep the rows of composed scroll frames and of
  settled tiles on the same device pixel, a spacer had to stay below 1000 px, so a box of 1000 px or more outside the area being rebuilt was cloned with all its children instead
  of being replaced. Table rows are never spacers, so F4's table (and its form) stayed in every tile: the markup of a one-line update went from 14 to 32 KB at 1,000 elements
  and from 21 to 67 KB at 2,000, the spacers from 83 to 195, the synchronous build at 2,000 from 2.2 to 5.9 ms (p50), and the decode task (SVG parse, layout and raster of
  the larger document) grew with it. Headless, the commit before it against it: 2,000 elements 0 / 1 / 2 against 25 / 56 / 57 tasks over 8.33 ms per 30 updates. Any page
  with a tall box outside the rebuilt area is affected, not only F4. Fixed in 0.1.0-preview.17 (`spacerHeight`: a tall spacer in two exact parts). Headed, 120 Hz, three runs:
  2,000 elements 56 / 56 / 24 against 4 / 7 / 0 tasks over 8.33 ms, 34.3 / 30.3 / 16.4 against 19.9 / 15.4 / 14.7 ms per update; 1,000 elements 17.7 / 23.0 / 12.8 against
  14.4 / 15.2 / 14.3 ms per update; the core of 2026-10-15 in the same session: 0 / 0 / 0 and 0 / 1 / 0 tasks over 8.33 ms, 20-22 and 17-19 ms per update. Update to pixel
  p50 stays at 3.0-3.5 ms.
- **A second cause, from 0.1.0-preview.2** (`Snapshot: cheaper clone walk with identical output`). A build whose synchronous part takes 3.5 ms or more starts its decode in
  the next task (`pump.js` `SPLIT_DECODE_MS`); otherwise the SVG is parsed, the tile lands at once, is drawn and the paint fires in the same task as the build. The cheaper
  walk brought F4's builds below that threshold (at 200 elements, split decodes 8-10 of 30 builds before it, 0-2 after; synchronous build p50 3.0 to 2.3 ms), so the
  whole update runs in one task of about 10-12 ms. This is what remains after the fix at 200 elements (headed: 21 / 20 / 22 tasks over 8.33 ms, against 10 / 4 / 2 with the
  core of 2026-10-15, at about the same total cost) and the 10-11 tasks at 1,000. Headless, the release before it against it at 200 elements: 5 / 1 / 3 against
  25 / 26 tasks over 8.33 ms (its third run was in the fast state described below). Measured as an experiment (headless, three runs, the fixed core with
  and without the threshold set to 0, so that every build that is not urgent decodes in the next task): at 200 elements 22 / 22 / 19 against 8 / 7 / 1 tasks over

## Method (what a number means)

- **Suite**: `test/bench/compare/` (`npm run bench:compare`, options `--subjects=ours,competitor,native --scenarios=typing,slider,click,scroll,resize,idle,firstpaint,memory,largedom,bundle`).
  One headed Chrome at a time, DPR 2 (`--force-device-scale-factor=2`), 120 Hz measured by rAF, throwaway profile, real window focus asserted before every pass.
  A load snapshot (`uptime`, top CPU; another process above 15 % CPU = machine load above threshold; waits up to 2 min) is stored before every scenario. Results: `.scratch/results/bench-compare-<subject>-<stamp>.json` (git-ignored); `report.mjs` regenerates the table (each scenario from the newest file that holds it).
- **Latency** = trusted event `timeStamp` → rAF timestamp of the first rendering update whose **canvas backing-store pixels** show the expected state (sampled by a MessageChannel task after each update; the screen shows it one refresh later, +8.3 ms). Correctness is part of the match, so a fast but wrong renderer cannot score:
  - typing, text fits: rightmost ink column ≥ the expected advance of the live value prefix (canvas `measureText`, same font) minus half a glyph; text scrolls: the column ink profile is classified against the round's first frame shifted by the live input's `scrollLeft` after every key (argmin over all states). Random wide letters per round (nonce) defeat image caching; 3 rounds × 12 keys at 120 ms and 30 ms;
  - slider: rightmost accent-colour column vs the value (calibrated on the two extremes every pass reaches), 2 sweeps, mouse every 8 ms;
  - click/focus, wheel tick, F4 author mutation: per-event baseline (last sampled frame) → first frame whose region differs by > 24 levels on ≥ 1 % / 2 % / 0.3 %.
  - every probe pass ends with a **pixel check against the plain-DOM twin** (same value / scroll offset / text / window size); "WRONG" marks a failure (> 3 % of pixels Δ > 16, or for text any Δ > 48).
- **Positive controls**: a frozen renderer (every `paint` swallowed and the 2D draw calls no-ops) must make every typing / slider / click / wheel sample "never drawn". All fire for all three subjects.
- **RunTask**: a separate traced pass of the same input without the probe (`RunTask` on `CrRendererMain` vs 8.33 ms; never the Long Tasks API). The probe was measured not to change the busy share or the longest task (`probe-effect.mjs`, measured once for the first edition of this document, 2026-10-14, with the core and browsers of that day: F1 typing RunTask p95/max/busy fresh vs after 4 s of readback: ours 0.82/6.7/10.0 % vs 0.22/7.2/10.3 %, other package 1.21/7.9/10.0 % vs 1.14/7.4/9.8 %, native 1.82/3.5/4.2 % vs 1.83/4.1/4.2 %).
- **Resize**: 30 real window drags (`Browser.setWindowBounds`, 12 steps, 16 ms, every third at 8 ms) between 1400 and 900 px; blank = canvas transparent/flat/zero-size in a sampled frame; convergence = last resize event → first frame from which the canvas never changes again before the next drag.
- **Idle**: renderer and GPU process CPU (`SystemInfo.getProcessInfo`) every second for 30 s, then a 10 s trace; caret blink verified on the canvas. **First paint**: rAF time (from navigation start) of the first frame with ≥ 90 % of the final canvas coverage; cold = new tab (new renderer process, HTTP cache cleared; the server sends `no-store` anyway), warm = same tab. **Memory**: 30 samples of `Runtime.getHeapUsage`, renderer RSS (largest renderer of our profile) and GPU-process RSS; heap after a forced GC. **Bundle**: `<script>` block time minus resource fetch time over 30 loads + one trace (V8 compile / evaluate).

## Where the polyfill loses, and why

Against **native**, input-to-pixel latency at p50 is within about one frame in every row of the table: equal for typing, the slider, resize convergence and F4 updates, ahead on the inner-list wheel (native's figure includes Chrome's smooth-scroll animation), about one frame behind on click to focus. First paint is 25-27 ms later in a new tab (38-39 ms in the same tab). Main-thread cost is 1.8-4.7x native per F4 update, and the busy share 1.1-4.3x native in the other traced scenarios (scroll stream 1.1x, typing 2.1x, slider 3.2x, resize 4.3x).
That is the floor of a userland approach: a snapshot has to be cloned, serialised, parsed, laid out and decoded by the browser before it can be drawn.

1. **Large drawables that change often** (F4): the picture of a one-line author update lands within one frame at every size (update to pixel p50 2.1-3.1 ms,
   native 2.8-3.6 ms), but the main thread spends 14.5-17.7 ms per update at 200-2,000 elements against 4-10 ms natively: the live page's own style and layout
   plus the clone, the serialisation and the isolated SVG document the browser has to parse, style and lay out. At 500, 1,000 and 2,000 elements that work is
   spread over tasks shorter than 8.33 ms (0, 1 and 0 of 30 updates ran a longer one; native 0, 0 and 18); at 200 elements 16 of 30 updates still run one task
   over it (longest 9.5 ms; native 0): the landing of the whole tile, about 8.4 ms by itself (see "What changed"). The damage is
   bounded to the children that moved and the tile leaves out what lies below it (a 60 Hz counter beside 2,000 elements painted 59 times a second when measured
   on 2026-10-15, see the optimization log). Keep frequently updated drawables small (`docs/guides/PERFORMANCE.md`).
2. **Click to focus pixel** (p50 14.6 vs 6.8 ms, p95 15.4 vs 7.7 ms): the caret appears at once, but an author `:focus` style needs a new snapshot, built inside
   the input task.
3. **First paint** (new tab: explainer 58.3 vs 31.6 ms, F1 91.1 vs 66.1 ms) and **startup** (342 KB minified core, 10.6 ms parse + compile + install, the first
   `paint` event 19.1 ms after script start): the core waits for 342 KB to be fetched and parsed (V8 compile 8.0 ms in the trace of the bundle scenario, 6.4 ms on 2026-10-15), the
   canvas's styles are resolved when its layer is mounted, and the first snapshot needs a clone, a serialisation and a decode.
4. **Memory** (F1: renderer RSS 203 vs 136 MB, GPU RSS 192 vs 128 MB): retained surfaces at DPR 2 and caches.
5. **Idle with a focused input** (47 RunTask/s, renderer CPU p50 2.1 % vs 1.1 %): the caret blink is painted into the retained surface.

Against the **other package**, this polyfill is slower on first paint (new tab: explainer 58.3 vs 38.1 ms, F1 91.1 vs 59.9 ms), startup (10.6 vs 1.9 ms), size
(342 KB vs 33 KB minified, about 116 KB vs 11 KB gzip; the other package's figure is the adapted bundle the bench loads), memory (F1 JS heap 3.1 vs 1.2 MB, renderer RSS 203 vs 199 MB),
main-thread busy share while typing (11.3 vs 8.6 %) and during resize drags (18.0 vs 7.5 %), and click to focus pixel at p50 (14.6 vs 7.7 ms in run B; 14.3 ms in run A). It is correct in every pixel check of the
table (in-field text scrolling, wheel scrolling, resize: 0 vs 542 blank frames), cheaper on large drawables at every size (F4 main thread 14.5-17.7 vs 23-70 ms
per update, update to pixel 2-3 vs 13-52 ms), and faster at p95 on typing, slider and click (typing every 30 ms 9.1 vs 43.8 ms, slider 8.3 vs 41.6 ms, click to
focus 15.4 vs 23.8-37.2 ms).

## Reproduce

```sh
node test/bench/compare/competitor/build.mjs                       # once: the other package's bundle (npm install of the pinned version into .scratch/)
npm run bench:compare                                              # ~45-75 min, all subjects and scenarios, then the report
node test/bench/compare/run.mjs --subjects=ours --scenarios=typing # one scenario; the report merges it in
node test/bench/compare/report.mjs                                 # regenerate the table only
node test/bench/compare/profile.mjs                                # V8 CPU profiles of ours (unminified bundle) on the losing paths
node test/bench/compare/breakdown.mjs [--only=f4|wheel|typing]     # self time per trace event inside long RunTasks (ours)
node test/bench/compare/probe-effect.mjs --subject=native          # does the readback probe change the page's cost?
```

Native needs Chrome Canary 157 or newer installed (the table: 159.0.8131.0); the harness launches it with `--enable-blink-features=CanvasDrawElement`.
