# Performance comparison: hic-live-polyfill vs html-in-canvas-polyfill 1.0.1 vs native

Three renderers on the same pages, in the same harness, with the same input: **ours** (`dist/hic-live-polyfill.iife.min.js`, Chrome stable,
no native feature), the **competitor** (the npm package `html-in-canvas-polyfill@1.0.1` = `three-html-render` 0.1.2, built by
`test/bench/compare/competitor/build.mjs` with an attribute adapter: it only knows `layoutsubtree`) and **native** (Chrome Canary + `--enable-blink-features=CanvasDrawElement`, no bundle).
Pages: the explainer example, F1 water form (effect off), F2 scroll, F3 resize, F4 large app (200-2000 nodes). Measured 2026-10-13 (native) and 2026-10-15 (ours, competitor) on one machine with no other busy process; ours' inner-scroll rows (4.) remeasured on 2026-10-19 with 0.1.0-preview.2.
The table below is generated; everything after it is written from these numbers, the CPU profiles and the trace breakdowns. "competitor" is only a short label for the other package.

## Method (what a number means)

- **Suite**: `test/bench/compare/` (`npm run bench:compare`, options `--subjects=ours,competitor,native --scenarios=typing,slider,click,scroll,resize,idle,firstpaint,memory,largedom,bundle`).
  One headed Chrome at a time, DPR 2 (`--force-device-scale-factor=2`), 120 Hz measured by rAF, throwaway profile, real window focus asserted before every pass.
  A load snapshot (`uptime`, top CPU; another process above 15 % CPU = machine load above threshold; waits up to 2 min) is stored before every scenario. Results: `.scratch/results/bench-compare-<subject>-<stamp>.json` (git-ignored); `report.mjs` regenerates the table (each scenario from the newest file that holds it).
- **Latency** = trusted event `timeStamp` → rAF timestamp of the first rendering update whose **canvas backing-store pixels** show the expected state (sampled by a MessageChannel task after each update; the screen shows it one refresh later, +8.3 ms). Correctness is part of the match, so a fast but wrong renderer cannot score:
  - typing, text fits: rightmost ink column ≥ the expected advance of the live value prefix (canvas `measureText`, same font) minus half a glyph; text scrolls: the column ink profile is classified against the round's first frame shifted by the live input's `scrollLeft` after every key (argmin over all states). Random wide letters per round (nonce) defeat image caching; 3 rounds × 12 keys at 120 ms and 30 ms;
  - slider: rightmost accent-colour column vs the value (calibrated on the two extremes every pass reaches), 2 sweeps, mouse every 8 ms;
  - click/focus, wheel tick, F4 author mutation: per-event baseline (last sampled frame) → first frame whose region differs by > 24 levels on ≥ 1 % / 2 % / 0.3 %.
  - every probe pass ends with a **pixel check against the plain-DOM twin** (same value / scroll offset / text / window size); "WRONG" marks a failure (> 3 % of pixels Δ > 16, or for text any Δ > 48).
- **Positive controls**: a frozen renderer (every `paint` swallowed and the 2D draw calls no-ops) must make every typing / slider / click / wheel sample "never drawn". All fire for all three subjects.
- **RunTask**: a separate traced pass of the same input without the probe (`RunTask` on `CrRendererMain` vs 8.33 ms; never the Long Tasks API). The probe itself was shown not to change cost (`probe-effect.mjs`: F1 typing RunTask p95/max/busy fresh vs after 4 s of readback: ours 0.82/6.7/10.0 % vs 0.22/7.2/10.3 %, competitor 1.21/7.9/10.0 % vs 1.14/7.4/9.8 %, native 1.82/3.5/4.2 % vs 1.83/4.1/4.2 %).
- **Resize**: 30 real window drags (`Browser.setWindowBounds`, 12 steps, 16 ms, every third at 8 ms) between 1400 and 900 px; blank = canvas transparent/flat/zero-size in a sampled frame; convergence = last resize event → first frame from which the canvas never changes again before the next drag.
- **Idle**: renderer and GPU process CPU (`SystemInfo.getProcessInfo`) every second for 30 s, then a 10 s trace; caret blink verified on the canvas. **First paint**: rAF time (from navigation start) of the first frame with ≥ 90 % of the final canvas coverage; cold = new tab (new renderer process, HTTP cache cleared; the server sends `no-store` anyway), warm = same tab. **Memory**: 30 samples of `Runtime.getHeapUsage`, renderer RSS (largest renderer of our profile) and GPU-process RSS; heap after a forced GC. **Bundle**: `<script>` block time minus resource fetch time over 30 loads + one trace (V8 compile / evaluate).

## Where the polyfill loses, and why

Against **native**, latency is within about one frame where the polyfill has a shortcut (typing in a single-line field, inner scrolling) and 1-2 frames behind elsewhere; main-thread cost is 2-8x native.
That is the floor of a userland approach: a snapshot has to be cloned, serialised, parsed, laid out and decoded by the browser before it can be drawn.

1. **Large drawables that change often** (F4): the picture of a one-line author update lands within one frame at 500-1000 elements (update to pixel p50 1.8-2.6 ms) and one to two frames
   later at 200 and 2000 (8-10 ms), against 2-3 ms natively, but the main thread still spends 17-22 ms per update at 200-2000 elements against 3-11 ms natively: the live page's own
   style and layout plus the clone, the serialisation and the isolated SVG document the browser has to parse, style and lay out. The damage is bounded to the children that moved and
   the tile leaves out what lies below it (a 60 Hz counter beside 2,000 elements paints 59 times a second, see the optimization log). Keep frequently updated drawables small
   (`docs/guides/PERFORMANCE.md`).
2. **Click to focus pixel** (p50 13.9 vs 5.7 ms, p95 15.6 vs 8.1 ms): the caret appears at once, but an author `:focus` style needs a new snapshot, built inside the input task. The
   polyfill rows of this metric moved by 5-8 ms for both polyfills between the 2026-10-14 and 2026-10-15 runs (the previous core measured 12.6-14.3 ms on 2026-10-15 too), so the
   2026-10-13 native figure is not a like-for-like reference here.
3. **First paint** (cold: explainer 66 vs 39 ms, F1 97 vs 71 ms) and **startup** (264 KB minified core, 8.1 ms parse + compile + install): the core waits for 264 KB to be fetched
   and parsed, about 11 ms of its first-run code is compiled on the main thread, the canvas's styles are resolved when its layer is mounted, and the first snapshot needs a clone, a
   serialisation and a decode (on F1 the first raster of the form alone is 11-15 ms).
4. **Memory** (F1: renderer RSS 200 vs 137 MB, GPU RSS 187 vs 127 MB): retained surfaces at DPR 2 and caches.
5. **Idle with a focused input** (47 RunTask/s, renderer CPU p50 2.1 % vs 1.1 %): the caret blink is painted into the retained surface.

Against the **competitor**, this polyfill is slower on first paint (cold explainer 66 vs 46 ms, F1 97 vs 69 ms), startup (8.1 vs 1.8 ms), size (264 KB vs 33 KB minified, 92 KB vs
10 KB gzip) and memory (F1 JS heap 3.0 vs 1.2 MB, renderer RSS 200 vs 195 MB). It is correct in every pixel check of the table (in-field text scrolling, wheel scrolling, resize: 0 vs
542 blank frames), cheaper on large drawables at every size (F4 main thread 17-22 vs 20-64 ms per update, update to pixel 2-10 vs 11-44 ms), and faster on typing, slider and click p95.

## Caveats

- Native runs on Canary 157 and the polyfills on stable 155: a different browser build. Native latency includes Chrome's own smooth-scroll animation for wheel ticks (the same for all subjects, since all scroll the live element).
- The competitor runs through an attribute adapter (it only knows `layoutsubtree`); its hit testing on the explainer uses the live element at x = 0 while drawing at x = 100 grid px (the click still lands, see [COMPARISON.md](COMPARISON.md)).
- The probe reads back one region per frame (0.9-1.9 ms p50 for ours); it runs identically on every subject and is excluded from every RunTask number.
- "Warm" first paint (same tab) is slower than "cold" (new tab) for all three subjects (the same tab first unloads the previous document); compare subjects within a column, not cold vs warm.
- Ours and the competitor: one full run each on 2026-10-15 (load average 1.4-2.4, no other process above 15 % CPU); native: the 2026-10-13 runs (Canary 157), reused. Ours' scroll scenario: rerun on 2026-10-19 with 0.1.0-preview.2 (Chrome 155.0.8059.80; load average 3.0 / 3.5 over one / five minutes, no other process above 15 % CPU at the start of the scenario); two runs gave 43.6 and 40.5 canvas updates/s and wheel p50 28.2 and 27.7 ms, the table shows the second. Before (0.1.0-preview.1): 36.8 updates/s, p50 28.5 ms, busy 24.2 %. macOS "Show scroll bars" is Automatic on the test machine and can switch between overlay and classic bars when a pointing device is attached; the reported runs used overlay bars.
- One machine (Apple M1 Max, macOS, 120 Hz, DPR 2). Nothing was measured on Windows or Linux.

## Reproduce

```sh
node test/bench/compare/competitor/build.mjs                       # once: the competitor bundle (npm install of the pinned version into .scratch/)
npm run bench:compare                                              # ~45 min, all subjects and scenarios, then the report
node test/bench/compare/run.mjs --subjects=ours --scenarios=typing # one scenario; the report merges it in
node test/bench/compare/report.mjs                                 # regenerate the table only
node test/bench/compare/profile.mjs                                # V8 CPU profiles of ours (unminified bundle) on the losing paths
node test/bench/compare/breakdown.mjs [--only=f4|wheel|typing]     # self time per trace event inside long RunTasks (ours)
node test/bench/compare/probe-effect.mjs --subject=native          # does the readback probe change the page's cost?
```

Native needs Chrome Canary 157 or newer installed; the harness launches it with `--enable-blink-features=CanvasDrawElement`.
