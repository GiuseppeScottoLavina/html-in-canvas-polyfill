# Bundles: what to load

`npm run build` (`scripts/build.mjs`, esbuild and Terser as devDependencies, zero runtime dependencies) writes seven classic IIFE bundles (each as a readable `.js` and a `.min.js`: esbuild's minified output given a second pass by Terser, with no unsafe transform and no property mangling), the same split as ES modules under `dist/esm/`, one classic and one ES module bundle per example plugin under `dist/plugins/` (with `manifest.json`), and `dist/sizes.json`. The size table below is generated by that build (bytes; gzip is level 9). `npm run check:bundle` (`scripts/check-bundle.mjs`, gate G-bundle) rebuilds, measures and loads every file in a headless Chrome.

> **Extensions are not the standard.** The frame cap (`framecap`, `canvas.frameCap`) and the effects host with its plugin interface (`HTMLInCanvasEffects`) are extensions of this library, not part of the HTML-in-Canvas proposal. Browsers' native implementations do not provide them. They run over the polyfill (mode `polyfill`) and over a browser's own implementation that the installed core stepped aside for (mode `native`), with the same bundles ([what differs there](guides/EFFECTS-PLUGINS.md#on-a-native-implementation)). The plugins are not part of the polyfill either: they are examples in [`plugins/`](../plugins/), each built into its own bundle.

## Which file for which use case

| use case | load, in this order | what you get |
|---|---|---|
| 2D only (`<canvas content="drawable">`, `drawElementImage`, `paint`, the frame cap extension) | `dist/hic-live-polyfill.iife.min.js` | `window.HicLivePolyfill`, installed on load |
| + Firefox 155+ / Safari 27+ (their form controls, classic scrollbars and shadows are drawn by the polyfill) | `hic-live-polyfill.iife.min.js` and `hic-live-engines.iife.min.js`, in any order | the Gecko / WebKit painters (not needed on Chromium; without them those engines keep the image look and the capture reports it once) |
| + WebGL / WebGPU texture upload of an element (`texElementSubImage2D`, `texElementImage2D`, `drawElementImageToTexture`, `copyElementImageToTexture`) | `hic-live-polyfill.iife.min.js` and `hic-live-gpu.iife.min.js`, in any order | the element-texture methods (without the bundle they exist and throw a NotSupportedError naming it) |
| 2D + effects (the WebGPU post-process host, plugin ABI, input interposer; an extension) | `hic-live-polyfill.iife.min.js`, then `hic-live-effects.iife.min.js` | + `window.HTMLInCanvasEffects` |
| + an example plugin, e.g. water | the two above and `plugins/water.iife.min.js` (any order) | + `window.HicLivePlugins.water` = `{meta, plugin, ...}` (WGSL inlined, no fetch) |
| Chrome 154-155 behind `--enable-blink-features=CanvasDrawElement` (the earlier `layoutsubtree` draft) or a native build missing a name the bridge can build | `hic-live-native-bridge.iife.min.js` BEFORE `hic-live-polyfill.iife.min.js` | mode `native-bridged` instead of the native build used as found |
| Chrome 157+ (complete native), Firefox 155+, Safari 27+ | Chrome: nothing extra; Firefox / Safari: `hic-live-engines.iife.min.js` with the core (row above) | complete native: mode `native` (the core does no snapshotting; the effects bundle runs over the native implementation); Firefox 155+ and Safari 27+: mode `polyfill`; older Firefox / Safari, web views and Firefox for Android: refused loudly (one `console.warn`, `window.__HIC__.error`). Phones and tablets: see [MOBILE.md](guides/MOBILE.md) |
| `ElementImage` in a dedicated worker (draw it on the worker's OffscreenCanvas) | the core in the page; `hic-live-worker.iife.min.js` at the top of the worker (`importScripts`), or `import '.../worker'` in a module worker | in the worker: `ElementImage`, `drawElementImage` on OffscreenCanvas 2D, the OffscreenCanvas geometry methods |
| download nothing where the browser implements the API (Chrome 157+), and the core (+ the engines bundle on Firefox / Safari) only where the polyfill runs | `hic-live-loader.iife.min.js` next to the other files, then `await HicLiveLoader.load()` before app code reads the API; bundlers: `import { load } from '.../loader'` | `{status, mode, installed, native}` ([API-CONTRACT section 2.4](API-CONTRACT.md#24-the-loader-loadoptions---promiseloadresult)); on Chrome 157 the page downloads 17,465 bytes (6,328 gzipped) instead of the core's 361,508 (123,063) |
| a bundler (Vite, webpack, rollup...) | `import { install } from '@giuseppe-scotto-lavina/html-in-canvas-polyfill'`, optionally `@giuseppe-scotto-lavina/html-in-canvas-polyfill/effects`, `.../plugins/water`, `.../native-bridge`; `.../worker` in a module worker | tree-shakeable ESM with shared chunks; each plugin is one self-contained module |

All scripts are classic `<script src>` tags (no `type=module`, no `import`), make no network request when they load (the loader requests the bundles only when `load()` is called), and the minified twins are drop-in replacements for the readable files (the gates and the mutants run the readable ones, G-bundle loads both).

```html
<script src="hic-live-polyfill.iife.min.js"></script>          <!-- installs synchronously; add data-hic-manual to call install() yourself -->
<script src="hic-live-effects.iife.min.js"></script>           <!-- optional: defines window.HTMLInCanvasEffects -->
<script src="plugins/water.iife.min.js"></script>              <!-- optional: window.HicLivePlugins.water -->
<script src="plugins/disintegrate.iife.min.js"></script>       <!-- optional: window.HicLivePlugins.disintegrate -->
<script type="module">
  // a module script only for its top-level await: the bundles above are classic scripts and run first
  const canvas = document.querySelector('canvas[content="drawable"]');
  const formElement = canvas.querySelector('form[drawable]');
  const host = await HTMLInCanvasEffects.createHost(canvas, formElement, { interposer: true });
  await host.addPlugin(HicLivePlugins.water.plugin, { intensity: 0.28 });
  const dust = await host.addPlugin(HicLivePlugins.disintegrate.plugin);
  formElement.addEventListener('submit', async (event) => {
    event.preventDefault();
    await dust.trigger('play');   // an action of the plugin (handle.trigger): resolves 'in' once the form has re-formed
  });
</script>
```

Size target: the design target for the minified core was 150 KB (gate G-bundle), and **the core in the table above is over it**. `npm run check:bundle` therefore prints the target as KNOWN RED and fails on any growth above a recorded ceiling (`scripts/check-bundle.mjs`), which is raised only deliberately, with a measured reason.

### Why the core has its size

`node scripts/build.mjs --analyze` prints where the bytes of the minified core come from. On 2026-10-22: `snapshot/capture` 31.5 %, `api` 19.5 %, `live` 16.8 %, `snapshot/store` 14.5 %, `schedule/observers` 9.2 %, the scheduler 3.8 %, `util` 3.1 %, `contracts` 1.5 %; the largest modules are the clone (6.3 %), the snapshot store (5.8 %) and the scroll emulation (3.9 %). The code that only some pages need (effects, the plugins, the native bridge, the Gecko / WebKit painters, the WebGL / WebGPU element textures, the worker side of a worker transfer) is already in separate bundles.

The core installs synchronously and must paint the canvas's first frame correctly for any page, so everything a first frame can need stays in it. Function coverage in Chrome on the 0.1.0-preview.4 core (the explainer, the fixtures F1 to F5 and three examples, each loaded and then used: typing, clicks, wheel scrolling, window resizes; macOS, overlay scrollbars): 62 % of the code ran by the first paint, 14 % only on interaction, 24 % never on those pages. Across those pages and the browser unit tests, the functions that never ran add up to about 22 KB of source, mostly the Chromium classic-scrollbar painter (G-platform runs it with classic bars): there is no significant dead code. What runs only on interaction cannot simply be loaded later: an autofocused field shows a caret in the first frame, a selection made by a script is painted in it, a classic scrollbar (the default on Windows and Linux) is drawn in it, and a scroller can start at any offset.

What could be loaded on demand without changing any pixel is a fast path that has a plain path behind it: the scroll compositor with its planner (`snapshot/store/scroll-compose.js`, `snapshot/capture/scroll-pages.js`) and the optimistic text overlay (`snapshot/capture/text-overlay.js`, `snapshot/store/text-paint.js`). Moved to a chunk fetched the first time an inner scroller or a typed key needs it, they take about 5.7 % off the core (17 KB minified, 6 KB gzip). This was measured and not adopted: the saving does not justify a runtime request from the library's own directory (with what that asks of CSP, SRI, CORS and Trusted Types) plus a second, complete core for pages that cannot make that request, while the cold first paint of the explainer over a 20 Mbit/s, 20 ms link improved by about 2 ms at the median (the F1 fixture within the spread between loads). Adopted on 2026-10-27: a Terser pass over esbuild's minified output (core -4.4 % gzip, -5.1 % brotli; every minified bundle smaller compressed), with options that change no behaviour (`TERSER` in `scripts/build.mjs`). Measured and not adopted: SWC, and mangling every property name that is not a DOM or JavaScript built-in (unsafe: option, report and event fields are public names).

### What the minified core is allowed to differ in

`HicLivePolyfill.FEATURES` in the classic core carries `{id, status}` per feature only (the `summary` / `reason` prose is about 32 KB of text, 12 KB gzipped, and nothing at runtime reads it; the store reads `status`). `docs/SUPPORT-MATRIX.md` has the prose and the ESM build keeps the full table. The build fails if a row of `src/contracts/features.js` does not have the expected one-line shape, and G-bundle compares the ids and statuses of the minified table with the source table.

The runtime reads a feature's status from `src/contracts/feature-status.js`, an id-to-status lookup that `npm run docs:sync` generates from `src/contracts/features.js` (G-doc-sync fails when it is stale), never from the public table. So in the ESM build `FEATURES` and `featureById` are used only by the entry's exports, and the table is marked pure: a bundler drops it, with all its prose, from an app that imports neither. Measured on 2026-11-02 with an app that imports only `install` from `dist/esm/index.js`, bundled and minified by esbuild: 435,465 bytes, 154,531 gzipped (level 9) before; 399,846 / 142,037 after (-35,619 / -12,494 bytes, -8.1 % gzip). The same app that also imports `FEATURES` is unchanged. G-bundle bundles both apps and fails if the first carries any `summary` or `reason` of the table or the second does not. The classic core answers the same lookup from its lean `FEATURES` (`lean-features` in `scripts/build.mjs`), so it holds each id and status once (+4 bytes minified).

## Load order and the seam between core and effects

- **Core first.** `install()` is SYNCHRONOUS by contract (API-CONTRACT section 2): it patches the prototypes during script evaluation, before app scripts read the API.
- **Effects second (or any time before `createHost`).** The core never imports effects code. It publishes a seam (`env` and `{store, scheduler, geometry, tracker}`) on the `HicInstalled` under `Symbol.for('hic.effects-seam')` (`createEffectsSeam` in `src/api/compose.js`); `HTMLInCanvasEffects` (`src/effects/index.js`, `createLateEffects`) looks the installed core up on every call. Before an install, after `uninstall()`, or without the core, `createHost` rejects with `InvalidStateError` ("needs the installed polyfill"); after a reinstall it works again. `uninstall()` destroys every host through the seam's `cleanups`.
- **Plugins in any order.** A plugin bundle has no dependency: it only registers its module under `window.HicLivePlugins`. `host.addPlugin` validates the definition (`definePlugin`), so a plugin needs the effects bundle only when it is used. The build checks every plugin folder against the contract of `plugins/README.md` before it bundles it.
- **Bridge before the core.** `install()` decides the mode synchronously. For a legacy or nearly complete native implementation it needs the bridge already registered.
- **The loader** (optional, instead of the core's tag) keeps that order itself: it makes `install()`'s decision, then adds the bundles it needs as `<script async=false data-...>` elements, which download in parallel and run in order (native bridge, engines bundle, core with `data-hic-manual`), and calls `HicLivePolyfill.install(options.install)` once they have run. Nothing for a native implementation it does not bridge, nothing for a refused browser. App code that reads the API waits for `load()`; one extra round trip comes before the core's download (measured below). The CSP it needs is in [API-CONTRACT section 2.4](API-CONTRACT.md#24-the-loader-loadoptions---promiseloadresult).

### What the loader costs and saves (measured 2026-11-04)

- Bytes on Chrome 157.0.8103.39 (native, Resource Timing, uncompressed server): a page with `hic-live-loader.iife.min.js` downloads 17,293 bytes of script (6,277 gzipped), with a plain tag of `hic-live-polyfill.iife.min.js` 351,362 (119,262 gzipped; the core of that build was 352,196 bytes minified, 119,615 gzipped), which then steps aside. The module loader's static imports were 35,217 bytes unminified (four files of `dist/esm/`); an app that imports only `load`, bundled and minified by esbuild with code splitting, started with 20,103 bytes (7,749 gzipped, three files: the shared chunks carry whole modules such as the patch ledger). Since 2026-11-05 (Chrome Canary 159.0.8137.0, G-native-loader) the classic loader downloads 17,465 bytes (6,328 gzipped; +172 / +51 for the option check before the window's load is taken) and the module loader 35,667 (five files); the module loader's polyfill path is in the next item.
- The decision takes 2.8 ms (`.min.js`) to 8.1 ms (the module loader, unbundled) from the module script to the settled result on that machine.
- First paint on the polyfill path (headless Chrome 157, native disabled, the `.min.js` files, a canvas with one drawable; 15 runs each, alternating, same machine): directly 60.5 ms median from navigation start, through the loader 70.8 ms (+10.4 ms) from a local server; with 40 ms of emulated latency per request 123.9 against 169.3 ms (+45.4 ms): the loader adds one request in series before the core's.
- The module loader's polyfill path (2026-11-05, gzip level 9, the sum over the files of each path, an app that imports only `load`, bundled and minified by esbuild 0.28 with code splitting; G-bundle holds these numbers to a ceiling): it imports `install()` and the GPU code from a private module (`chunks/loader-core-*.js`) rather than the package entry, because a bundler keeps every export of a module imported with `import()`, which carried the whole `FEATURES` table and the engines into that path. Start 8,030 bytes (7,749 when the loader imported the package entry; +281 for a fourth file, the user-agent parser now shared with the engines chunk); polyfill path on Chromium 134,325 (163,227 when the loader imported the package entry, -17.7 %), on Firefox and Safari, which also fetch the engines chunk, 150,902 (-7.6 %); with the core of 0.1.0-preview.23, 132,220 (161,057 with the package entry) and 148,797; before the scroll compositor's cover and pin checks, 130,633 and 147,210 (159,020 with the package entry). - The consumer's bundler must keep the dynamic imports as separate chunks. Vite, webpack and rollup split `import()` by default; esbuild needs `splitting: true` (with `format: 'esm'`). - Size: 6,277 bytes gzipped against the 5 KB goal (6,328 since 2026-11-05). About 4,340 of them are `install()`'s decision (the probe, the browser gate and the decision table with their texts, about 3,310; the option validation, about 1,030), shared with the core rather than reimplemented; the script loading and the result about 1,935.

## The Chrome core, the engines bundle and the GPU bundle

The classic core is what a Chromium page loads, so code that only another engine or an optional API needs is outside it, in explicit opt-in bundles that make no request by themselves (the contract above: every bundle is a plain `<script src>` the page lists):
- `hic-live-engines`: the Gecko / WebKit form-control skins ported from the engines' painters (`native-controls.js`, `webkit-skins.js`, `gecko-skins.js`), the WebKit classic scrollbars (`webkit-bars.js`), the WebKit shadow rewrite (`webkit-shadow.js`), Safari's accent caret for `caret-color: auto` on macOS (`webkit-caret.js`; without the bundle the caret keeps the text colour) and the style rules for the controls it paints (added to every clone's base sheet while it is registered). Chromium draws native controls inside SVG images itself, so the core never needs them there. The capture looks the painter up through `snapshot/capture/engine-skins.js`; on Firefox / Safari without it, it reports `engine-gecko` / `engine-webkit` once.
- `hic-live-gpu`: WebGL / WebGPU element textures (`api/texture-patch.js`, `texture-math.js`), registered for `api/gpu-seam.js`. Without it the four methods still exist (feature detection unchanged) and throw a NotSupportedError naming the bundle; loaded after the core it replaces the stubs of the installed core.
- Not moved: the OffscreenCanvas transfer patch (the 2D patch depends on it), the page side of a worker transfer (`api/worker-transfer.js`: it rewrites the page's own postMessage) and the fullscreen guard.
- `hic-live-worker`: the worker side (`api/worker-scope.js`), which only a worker loads.
- The ESM package entry imports both, so bundler users keep one import for everything.

## What had to stay in the core, and the native-bridge decision

Core = the 2D polyfill: native detection (`native-detect.js`: it decides between "nothing to do", "polyfill" and "refuse", so it cannot be lazy), options, registry, patches (canvas, 2D, offscreen, texture variants, guards), live layer, selector bridge, capture (clone, CSS, scroll emulation, caret), snapshot store and pump, scheduler, observers, reporter, and the effects SEAM (`createEffectsSeam`, a dozen lines of `api/compose.js`).

Moved out: the effect host, plugin ABI, GPU presenter, source providers, input mapper, interposer and frame sources (the effects bundle), the plugins (outside `src/` altogether, in `plugins/`), and the native bridge (`native-bridge.js` + `native-geometry.js` with its glue). Their sizes are in the generated table above.

Native bridge, with the evidence for "separate script, not lazy":
- It is only needed for a LEGACY native (Chrome 154 and 155 behind a flag) or a native missing a name it can build. Chrome 157 and Chrome Canary (a complete native, enabled by default; measured on Chrome 157.0.8103.39: kind `complete`, no gaps) need nothing of it, and 154-156 without the flag has no native, so the polyfill path runs. No gate runs the bridged mode end to end; its unit tests (`test/unit/api-core/native-bridge.browser.test.mjs`, `install.browser.test.mjs`) load it through the same registration as a page would.
- It cannot be fetched lazily: `install()` is synchronous (a fetch would make it asynchronous), the IIFE auto-installs during evaluation, and G-bundle requires no network request at load. So it is a second script that the page includes on purpose. When it is missing the core never throws: it uses the native build as found (mode `native`), records a `native-step-aside` entry in `report().deviations` that names the built files `dist/hic-live-native-bridge.iife.min.js` (or the readable `hic-live-native-bridge.iife.js`), and for the earlier `layoutsubtree` draft prints one `console.warn`, because `content="drawable"` canvases are not drawable there without the bridge.
- The loader (`hic-live-loader`, `esm/loader.js`) is the opt-in shell that fetches the core only where it runs. It does not change `install()`, which stays synchronous: the page that chooses the loader accepts an asynchronous start, and the core's own tag keeps the synchronous one. It fetches the bridge only for a native build the bridge can bridge, before the core.

## Behaviour changes against the single-bundle layout

1. `window.HTMLInCanvasEffects` exists only when `hic-live-effects.iife.js` (or `installEffects()` of the ESM entry) ran. Before, the core defined it on install and removed it on uninstall; now it stays defined after `uninstall()` and its `createHost` rejects until the next install.
2. A legacy or nearly complete native is bridged only when the bridge bundle is loaded; without it the native build is used as found (mode `native`, above).
3. The classic core's `FEATURES` has no `summary` / `reason` (above).
4. A built plugin never fetches its `.wgsl` files (they are inlined at build time). Served as source (`plugins/<name>/index.js`) it fetches each one once through its `wgsl.js`, the only module the build swaps.
5. `package.json` `exports`: `.` is `dist/esm/index.js`; `./effects`, `./native-bridge` are the ESM entries; `./plugins/<name>` is a plugin's ES module (types in `dist/types/plugins/<name>/`), `./plugins/<name>/iife` and `./plugins/<name>/iife/min` its classic files, `./plugins/manifest.json` the list; `./worker` is the ES module of the worker side (types in `dist/types/worker.d.ts`); `./loader` is the module loader (types in `dist/types/loader.d.ts`); `./iife`, `./iife/effects`, `./iife/native-bridge`, `./iife/engines`, `./iife/gpu`, `./iife/worker`, `./iife/loader` (each with a `/min` twin) are the classic files. The sources under `src/` ship for reference (the readable `.iife.js` and ESM builds are not minified; no source maps are published) but are not an entry point: they are internal and change without notice. The plugin subpaths are patterns, so a new plugin needs no change to `package.json`.

## Checks

- `npm run build`: the artifacts above plus `dist/sizes.json`; it fails when a plugin folder breaks the contract of `plugins/README.md`.
- `npm run check:bundle` (`npm test` and CI run it with `--allow-size`): `dist/sizes.json` against the files in `dist/` (so `--no-build` never judges a file rebuilt or edited since by its old size); sizes against the size budget, the measured size plus a small margin (min files; core 361.75 KB, effects 40.25 KB, bridge 13.5 KB, engines 45.875 KB, GPU 11.5 KB, worker 9.25 KB, loader 17.5 KB; gzip level 9: core 123.25 KB, effects 14.25 KB, bridge 5 KB, engines 17.5 KB, GPU 4.5 KB, worker 3.75 KB, loader 6.5 KB; each plugin its measured size plus a small margin (`PLUGIN_LIMITS`: crt 11.5, disintegrate 27.75, glitch 16, holo-card 17.25, liquid-glass 19.85, page-curl 37, shatter 36, water 25.75 KB) and 16 KB for a plugin not listed there; 1 KB = 1000 bytes, as in the target) and the 150 KB target; each IIFE parses as a classic script and has no dynamic `import()`; no file under `dist/` contains a path of the build machine; in headless Chrome, for the readable and the minified files: core alone, core + effects (including `createHost` rejecting after `uninstall()`), core + effects + each plugin of `dist/plugins/manifest.json` (it registers, `definePlugin` accepts it, its shader modules receive inlined WGSL strings), bridge + core, core + engines, core + GPU, the loader alone and the loader with the core it loads (ten concurrent `load()` calls: one request, one install, `whenPainted`; a core slower than `timeout`: status `error`, and once it arrives no install, no layer, no patched prototype; a 404; a nonce-only CSP without and with `nonce`), each with ZERO requests beyond the declared scripts and each declared script requested exactly once (server log and Resource Timing) and no page error (on a machine without a WebGPU adapter the documented `effect-plugins` report of `createHost` is the one console error allowed in core + effects); the ESM build as native modules, and the ESM loader (ten concurrent calls, its core module `chunks/loader-core-*.js` requested once, neither the package entry nor, on Chromium, the engines; a classic-only option rejects); an app that imports only `load` from `dist/esm/loader.js`, bundled by esbuild with code splitting, keeps the `FEATURES` prose and the engines out of its Chromium polyfill path and stays within its gzip ceilings (start 8.1 KB, polyfill path on Chromium 134.5 KB, on Firefox / Safari 151 KB). Its controls: a module is not a classic script, a dynamic import and an oversize bundle are seen, the loader app whose loader imports the package entry carries the prose and the engines, an undeclared script is an unexpected request, a script requested twice is reported, a missing global is reported, and in the timeout case an explicit `install()` of the late core is seen by the same patch check.
- `node test/native-effects/g-native-loader.mjs --chrome=<Chrome 157+>` (stage `loader` of `npm run test:native-effects`): on a browser that ships the API, the classic loader (`.js`, `.min.js`) and the module loader settle `status: 'native'` with ZERO requests for the core, the engines bundle or the bridge and no member carrying the polyfill's patch mark; control: the same pages with the native API disabled download the core and install.
- `npm run test:examples` (`scripts/check-examples.mjs`) loads the minified bundles from `dist/` in the seven pages of `examples/` (the plugin gallery, `effect-plugin` and the playground's sandboxed preview included) and in the two smoke pages of `test/examples-smoke/` (the ESM entry `dist/esm/index.js` and a plugin written against `hic-live-effects.iife.min.js`), in headless Chrome, with a control that breaks the `dist/` path.
- The browser gates (`test/gates/`) load the core, and the effects bundle and `dist/plugins/water.iife.js` for the effect gates, from `dist/` through `--bundle-file`, `--effects-file` and `--water-file`; the mutant suite mutates the core, the effects file (`bundle: 'effects'`) or the engines file (`bundle: 'engines'`, served to G-xbrowser through `--engines-file`) and runs the gates on it.
