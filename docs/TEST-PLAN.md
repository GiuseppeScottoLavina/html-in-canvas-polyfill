# Test plan

The gate list with exact oracle definitions and thresholds. A gate is a command that exits non-zero when a promise breaks. The harness (`test/harness/`, see its README), the repo gates (`npm run lint`, `npm run check`), the unit tests and the browser gates of section 2.8 (`npm run test:gates`, `npm run test:mutants`, `npm run test:gates:all`) are implemented; the other rows are planned (`to write`).
The list is derived from the project's testing rules (section 0). Rows marked `to write` are planned and do not exist yet.
Timing thresholds that depend on the decode cost (G-typing, G-throughput, G-large-dom) are set ONLY from a run with no machine load above threshold (`G-decode-main`).

## 0. Rules every gate obeys

1. **Real headed Chrome**, foreground, focused (`page.ensureForeground()` before and after each measured window; a run that lost focus is DROPPED, never counted: the gate runner reports `verdict: NOT USABLE`, `pass:false` when the focus mode is `failed` or focus was lost inside a measured window, and flags `focus:cdp-click` (the OS refused to activate the window, a trusted click in the page corner was used) as DEGRADED), 120 Hz where
   available (the report states the measured rAF period), throwaway profile under `.profiles/`, own PID only. DPR 2 (native on the dev machine) and DPR 1 (`launchChrome({dpr:1})`).
2. **Trace-based timing.** Main-thread cost = `RunTask` on `CrRendererMain` from a Chrome trace (`analyzeTrace`), compared with 8.33 ms (120 Hz) and 16.7 ms. The Long Tasks API
   (50 ms threshold) is never an oracle. Traces are bracketed with `performance.mark('m0'/'m1')` so setup is excluded; windows are short (the harness reads trace streams in <= 1 MB chunks).
3. **Surface assertion + positive control in every performance/correctness gate, one control class per check class.** Each gate first proves its detector can fail: a broken renderer (blank canvas, stale canvas, wrong
   hit target, uncapped loop) must turn the gate red in a `--control` run, and the real run asserts the surface is non-blank (`surfaceNonBlank`, content score) before it looks at any
   number. A gate whose control does not fail is itself failed (`G-meta-controls`). Each check carries a CLASS (`pixel`, `region`, `content`, `hit`, `typing`, `blank`, `latency`, `layout`, ...); a gate declares the classes its control must turn red (`controlClasses`) and the gate fails when a declared class stayed green ("some check went red" is not enough). The sabotage is applied BEFORE the first paint (it is appended to a copy of the bundle served under a control URL), never after.
4. **Pixel oracle vs plain DOM**, read from the CANVAS BACKING STORE (`readCanvas`, composited over the canvas background) for 2D surfaces, NEVER from a compositor screenshot that could contain the live DOM (the layer is `opacity:0` over the canvas; a leak or a layer-over-nothing must not pass). Every 2D pixel gate also asserts the layer's computed opacity is 0 (class `leak`), asserts the twin has content (a blank cannot fit the budget), compares per-element rectangles, and runs a tight pass (delta > 4-6) next to the 3 % / delta > 16 project gate. WebGPU surfaces are judged from screenshots taken with the layer forced invisible (`filter:opacity(0)`: `visibility`/`display` would blank the snapshot, which reads inherited styles from the layer) (`compareToTwin` of `test/gates/lib/pixel.mjs`): same window, two tabs, same DPR, `--force-color-profile=srgb`, surface composited over its CSS background; verdict `fraction = pixels with
   any channel delta > 16 / total <= 0.03`, ALWAYS with the exact numbers (`diffPixels`, `maxDiff`, `countOver16`, bbox) recorded. A blank surface fails whatever the diff. Effect-on surfaces
   (WebGPU) are read with `screenshot`, never canvas readback (unreliable).
5. **Cadence honesty.** Every injector reports the cadence it REALLY achieved (`paced().actual`, `effectiveHz`, page-side `readEventProbe`); a gate with `cadenceOk:false` is dropped.
6. **Machine load.** Before EVERY measured run record `loadSnapshot()` (uptime + top CPU processes) and store it with the result; another process above ~15 % CPU: `waitForQuiet` up to a few
   minutes, then retry, else mark the result `highLoad` (machine load above threshold: reported, never used for a threshold decision). Never kill or attach to anything not spawned by the run.
7. **Never judge by the demo's own badges, nor by the polyfill's own counters**: the frame cap is judged from an independent clock (`GPUCanvasContext.getCurrentTexture()` stamps from a page-side tracker), install is judged from the public API names, `report()` is read only by the gates whose subject is the report (G-unsupported, G-regress-stacking). A badge that measures its own rAF can hide the cap behaviour. Counters come from page-side event timestamps and traces.
8. Each gate prints one JSON line `{gate, pass, numbers, control, load, chrome, dpr, rafHz}` into `.scratch/results/` and a human summary; failures name the first violated threshold.

**Verdict and reporting.** `verdict` is `PASS`, `FAIL` or `NOT USABLE`. `degraded` lists `high-load` (another process above 15 % CPU; `--wait-quiet=SECONDS` waits for a quiet window first), `focus:cdp-click`, `no-control` (`--no-control` is explicit and such a row is never green), `screen-locked`, and `foreign-pointer:N`, which also makes the run NOT USABLE.

**A gate that hangs reports itself.** A gate still running after `--watchdog-min` minutes (default 10; the longest gate takes under 3) closes its browser and reports FAIL with the CDP calls it was waiting for, or NOT USABLE when the screen is locked (a locked screen stops `requestAnimationFrame`, and canvas reads wait inside one). Before, such a gate printed nothing until the runner killed it, and the mutant suite read the empty output as a result and crashed at its first baseline; `run-all` and the mutant runner now report any gate process without a result line as NOT RUN with the reason (exit code, signal, runner timeout).

**Pointer input the gate did not send.** A headed Chrome on macOS delivers the operating system's pointer to the page whenever the view geometry changes under a resting pointer: every `Page.captureScreenshot` with a `clip` (it runs through a device-emulation pass) and every tab activation sends a trusted `mousemove` at the pointer's place (measured with Chrome 155). A pointer left over the test window therefore moved `:hover` behind the gate's back: G-scroll-cadence's plain-DOM twin lost the hovered row it had been given at each element screenshot (one row band 6.3 % different, "flaky" at both DPRs), and a range slider under the pointer was drawn in its hover look in G-f1-form. `launchChrome` moves the OS pointer out of the new browser window when it rests over it (`browser.pointerPark`; `HIC_PARK_POINTER=0` turns it off), and every gate page carries a pointer guard (`Page.installPointerGuard`) that records each trusted `mousemove`, `mousedown` and `wheel` at a position the harness never sent (someone using the machine, a Universal Control link, the resting pointer when it could not be moved). Such a run is `NOT USABLE` and its first failure reads `ENVIRONMENT: pointer input the harness did not send reached the page`, never a product result. Input that arrives while the page is fullscreen, or within 2.5 s of a fullscreen change, is only recorded (`fullscreenPointer`): a fullscreen window covers its whole display, so the parked pointer is over it (G-unsupported's fullscreen check). The harness selftest (`--only=pointer`) proves both controls: an unrecorded trusted event and, on macOS, the real pointer placed over the page and delivered by a clipped screenshot are reported, and a clipped screenshot with the parked pointer delivers nothing. `countsForThresholds` is true only for a PASS with nothing degraded. `summary-green.json` is written only when every row of a full `run-all` is PASS with its control and nothing is degraded.

**Mutant suite (`npm run test:mutants`, `test/gates/mutants/`).** Each mutant is a string edit of a COPY of `dist/hic-live-polyfill.iife.js` (or of `dist/hic-live-effects.iife.js` for a mutant with `bundle: 'effects'`, served with `--effects-file`; built under `.scratch/mutants`, the repo's dist is never touched; every anchor must occur exactly once, else `ANCHOR DRIFT` fails the suite). ## 3. Reporting

`npm run test:gates` (`test/gates/run-all.mjs [--only=ids] [--no-control] [--dpr=N] [--wait-quiet=S]`) runs gates sequentially (ONE browser at a time), prints a table, writes `.scratch/results/<gate>-<timestamp>.json` with the numbers listed in section 0.8, and

A gate that cannot run says `NOT RUN: <reason>` and counts as failed in the summary, never as passed.

**Scroll jank measurements (reported data, no thresholds).** `node test/bench/scroll-jank.mjs` (headed Chrome, headless with `--headless`; `--cases`, `--rates=1,4,6` CPU throttling through `Emulation.setCPUThrottlingRate`, `--inputs=wheel,touch` trusted wheel events and `Input.synthesizeScrollGesture` touch drags with their fling, `--touch-cold` for a touch stream with no pointer hovering first, `--profile`, `--bundle`, `--dpr` for a forced device pixel ratio): three gestures with pauses per run on the scroll-cadence fixture (plain, rounded, `:hover` rows, 2000 rows, two scrollers the compositor refuses), F2 and the scroll-and-resize example. ## 4. Where the gates run

On every push the `CI macOS` workflow (`.github/workflows/ci-macos.yml`) runs on GitHub-hosted macOS runners: the Chrome gates that do not depend on the refresh rate or on continuous WebGPU frames, each with its control, at DPR 2 forced on the runner's 1x 60 Hz virtual display (`HIC_GATE_DPR`; G-regress-capture and G-pixel-dpr keep their own ratios), the mutants whose gates all run there (one per gate on pull requests, all of them nightly and on release tags), the headless suites, and G-xbrowser on Firefox (all scenarios but scroll, which at the runner's DPR 1 exceeds its pixel bound). The thresholds are the ones of this document, unchanged. A gate whose promise depends on the 120 Hz display (G-scroll-cadence), on throughput the shared 3 vCPU runner sits on the edge of (G-regress-paint-rate: the paint rates of M5 and M6, whose correctness checks are G-regress-paint and run in CI), G-scroll-inner (its page-scroll step differed there once, not yet explained), on continuous WebGPU frames (G-f1-form-effect, G-interposer-strong, G-native-effects, G-native-interposer, the plugin gallery tests), G-wpt-subset, G-xbrowser on Safari (the runner images ship Safari 26, below the supported 27) and Safari Technology Preview, and G-mobile run locally (`npm run test:local`). `test/ci/macos-plan.mjs` holds that list with the measured reason of each entry; every CI run prints it, so nothing is left out silently. Results measured on the runner carry its environment record (`.scratch/results/macos-env.json`: display, refresh rate, GPU, WebGPU adapter, session) and are never used to set a threshold.
